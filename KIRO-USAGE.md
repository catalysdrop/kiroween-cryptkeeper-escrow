# How Kiro was used — honest statement

This document exists because Kiroween judges Kiro usage, and because
faking tool usage would be worse than admitting a gap. Here is exactly
what happened.

## What Kiro did in this build

1. **Kiro CLI was installed and verified in the build environment.**
   `curl -fsSL https://cli.kiro.dev/install | bash` installed
   **Kiro CLI 3.6.2** (`~/.local/bin/kiro-cli`, verified with
   `kiro-cli --version` on 27 Nov 2026). The binary runs; `whoami`
   reports the session state.
2. **The build followed Kiro's spec-driven workflow.** The feature was
   planned as a Kiro spec before any code was written:
   `.kiro/specs/cryptkeeper-escrow/` contains `requirements.md` (user
   stories + acceptance criteria), `design.md` (architecture, state
   machine, decisions) and `tasks.md` (wave-ordered implementation
   tasks, checked off as they landed).
3. **Steering docs** (`.kiro/steering/product.md`, `tech.md`,
   `structure.md`, `security.md`) state the product, stack, layout and
   the non-negotiable security rules the code follows — including
   "never move real funds / no mainnet", which the contract and the
   hooks enforce.
4. **Agent hooks** (`.kiro/hooks/*.json`, schema `v1`, verified against
   https://kiro.dev/docs/hooks) automate the workflow Kiro documents:
   lint-on-save, test-on-save (agent unit tests + `forge test`), and a
   `PreToolUse` guard that blocks mainnet deploys and checks commits
   for secrets.
5. **Custom agent** (`.kiro/agents/crypt-keeper.json`) defines the
   Crypt Keeper persona with the project's steering files as resources,
   so a Kiro session working on verdict logic loads the same rules.
6. **MCP settings** (`.kiro/settings/mcp.json`) document the MCP
   surface (filesystem server present but disabled by default, with the
   reason stated).

All `/.kiro` artifacts use the formats documented at kiro.dev
(specs, steering frontmatter, hooks schema v1, agent resources glob)
and were validated: hook/agent JSON parses, steering frontmatter is
well-formed, and `/.kiro` is **not** in `.gitignore`.

## What Kiro did NOT do (the gap)

**Kiro CLI could not be authenticated in this build environment, so no
code in this repo was generated by a logged-in Kiro session.** The
CLI reports `Not logged in`. Logging in requires either:

- a browser sign-in with a Builder ID (`kiro-cli login`), or
- a `KIRO_API_KEY` for non-interactive use.

Neither was available in the sandboxed build environment (no live
browser, no API key), and no credentials were fabricated or borrowed.
The implementation code (Solidity, TypeScript, Next.js) was therefore
written and tested by the author's coding agent (Muse) following the
Kiro spec, steering and hooks above — not by Kiro itself.

## How to complete the Kiro loop

Anyone with a logged-in Kiro session can pick this repo up and make
the Kiro usage fully live in minutes:

```bash
kiro-cli login            # or: export KIRO_API_KEY=...
cd kiroween-cryptkeeper-escrow
kiro-cli chat             # the spec, steering and hooks load automatically
# then, e.g.: "Run the tasks in .kiro/specs/cryptkeeper-escrow/tasks.md
#              that are still unchecked, and add property-based tests
#              for the Keeper's scoring thresholds."
```

The spec's task list is written so Kiro can execute it (dependency
waves, verifiable outcomes per task). The hooks will then fire on real
Kiro sessions: lint on save, tests on save, mainnet-deploy guard on
every `forge`/`cast` invocation.

## Why this is disclosed this way

Kiroween's rules disqualify inadequate Kiro usage. Claiming "built
with Kiro" while the CLI never ran would be a false claim. This
document states the facts so judges can weigh the real Kiro artifacts
(spec-driven process, steering, hooks, custom agent, installed CLI)
against the missing piece (an authenticated Kiro session) — and so the
author can close that gap before submission by running the steps
above from a logged-in machine.
